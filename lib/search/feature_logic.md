## 目标

解决简→繁一对多、繁→简一对多、经文被误转、搜索结果不确定等问题，同时保留 Goto 搜索。

本章节结论：方案总体可行，但需要按后文修订执行。候选生成后**不搜索本地经文、不计算统计数量**，只负责让用户确定实际搜索词。

---

## 一、结论：方案总体可行，但需要修正

原方案方向正确：

- 把映射表从「一对一」改成「一对多（列表）」；
- 用保留词库消歧；
- 多候选时让用户选择（不统计本地经文命中数量）；
- 繁→简用词库保护经文。

但原方案有几处需要修正，否则会出现组合爆炸、接口压力、离线不可用、输入判定不可靠等问题：

1. **按字组合可以生成，但不做任何统计**：多个歧义字会产生较多组合；本方案只在本地生成候选，既不向服务器发计数请求，也不扫描本地经文。
2. **候选生成是纯前端字符串处理**：最长词库匹配 + 单字兜底 + 组合上限，同步完成，不启动 isolate、后台任务或计时器。
3. **「确定是繁体」无法百分之百判断**：简繁共用字（如「后、里、云、干」）没有字形差异，只能保守判定。
4. **候选只需要排序，不需要计数**：排序依据静态优先级（词库推荐、原字、首选字形等），不使用「作品数」「卷数」「出现次数」等统计结果。
5. **下拉框不应是自由文本编辑框**：移动端输入法 + 浮层容易冲突，建议只读下拉/底部弹层。
6. **所有搜索入口都要统一**：首页搜索、全文搜索页、卷内搜索、经目搜索、AI 搜索的行为要明确。
7. **Goto 必须在任何转换之前判断**。
8. **繁→简不能只靠单字列表**：必须词组优先，否则「乾闥婆」「著」「藉」等仍会转错。
9. **候选生成还需要考虑用户输入与历史**：至少含一个繁体字时原文应作为候选；与历史高度匹配时历史选择应优先。

值由字符串改为**有序候选数组**：

```json

  "发": ["發", "髮"],
  "干": ["干", "乾", "幹"],
  "后": ["后", "後"],
  "里": ["里", "裡", "裏"],
```

规则：

- 数组内去重；
- 顺序即推荐顺序；

## 三、输入文字类型判定

### 3.1 三个字符集合

- `SIMPLIFIED_ONLY`：只可能是简体、繁体语境不会单独使用的字；
- `TRADITIONAL_ONLY`：只可能是繁体、简体体系不会使用的字；
- `SHARED`：简繁同形（后、里、云、干、面、谷……）。

由两张表自动推导，并允许人工覆盖。

### 3.2 判定结果

| 输入情况 | 判定 | 行为 |
|---|---|---|
| 只含 `TRADITIONAL_ONLY` 或 `SHARED` | 繁体/中性 | 直接搜索原文 |
| 只含 `SIMPLIFIED_ONLY` 或 `SHARED`，且至少一个 `SIMPLIFIED_ONLY` | 简体 | 进入候选生成 |
| 同时含 `SIMPLIFIED_ONLY` 与 `TRADITIONAL_ONLY` | 混合 | 仅转换简体部分，优先按词库处理 |
| 只有 `SHARED`、数字、拉丁字母、标点 | 中性 | 直接搜索原文 |
| 空输入 | 无效 | 不搜索 |

注意：

- 用户只输入「后」「里」「云」时无法判断简繁，按中性处理，直接搜索原文；
- 不要仅凭码位判断，必须以字符集合为准；
- 混合输入的候选生成只针对简体片段，繁体片段原样保留。

## 四、简 → 繁候选生成

### 4.1 首页关键字搜索先做 Goto 判断（最高优先级）

仅**首页关键字搜索**在转换与候选生成之前做 Goto 判断：

1. `extractCbetaGotoQuery(rawInput)`；
2. `normalizeCbetaGotoLinehead`；
3. `isCbetaGotoExpression`。

若命中，直接走原有 Goto 流程，**不进入候选选择**。

以下入口**不做 Goto 判断**：

- 卷内搜索；
- 经目搜索；
- 作译者搜索；
- AI 语义搜索。

这些入口把输入当作普通关键字处理。

### 4.2 词组优先 + 单字兜底

生成算法：

1. 对输入做**最长匹配**的词库查找（`phrases_simplified_to_traditional`）；
2. 命中词库的片段直接采用其候选（推荐项第一）；
3. 未命中的片段逐字查简→繁列表；
4. 每个位置合并候选并去重；
5. 组合时做上限控制。

### 4.3 候选组合的生成与上限

组合可以生成得较多，但**既不向服务器发计数请求，也不扫描本地经文**。为避免候选过多，仍建议：

- 每个歧义位置最多保留 **3** 个候选；
- 单次查询最多生成 **50** 个组合，下拉框最多展示 **20** 个；
- 超过上限时保留优先级最高的组合，并提供「编辑查询」入口；
- 若只有一个组合，直接搜索，不弹框；
- 若输入被判定为繁体，不转换、不弹框。

### 4.4 候选排序规则

排序只使用静态规则，不依赖任何命中统计，也不读取本地经文：

**固定优先项（置顶）**：

1. **与搜索历史高度匹配的结果**（见 4.6）；
2. **输入中至少含一个繁体字时，原始输入本身**（见 4.5）。

**其余候选**：

3. 按候选生成顺序（即基础优先级）：
   1. 保留词库推荐项；
   2. 原字（简繁共用字）；
   3. OpenCC 首选；
   4. 台湾常用字形；
   5. 其他候选。

> 固定优先项始终置顶，不参与基础优先级排序。

> 若历史匹配与原始输入同时成立，默认**历史匹配优先**：它是用户在相同输入下明确选择过的结果。若产品希望“原文优先”，可将两者顺序对调，但必须保持全应用一致。

### 4.5 输入含繁体字时的原始输入优先

若满足以下条件：

- 输入中**至少有一个仅繁体字**（`TRADITIONAL_ONLY`）；
- 同时存在多个转换候选；

则把**用户原始输入**作为候选之一，并按 4.4 的规则置顶（若没有历史匹配）。

理由：

- 用户既然输入了繁体字，原文很可能就是他想搜的内容；
- 混合输入直接搜索原文，比强制转换更符合直觉；
- 原始输入若已等于某个候选，需要去重。

注意：若输入全部为繁体字，仍按既有规则直接搜索，不弹候选框。

### 4.6 搜索历史优先

当新输入与历史记录高度匹配时，将历史上实际使用的搜索词作为第一候选。

「高度匹配」建议定义为：

1. 与历史 `rawInput` 完全相同；
2. 或历史 `rawInput` 是新输入的前缀/包含关系，且长度 ≥ 2；
3. 或归一化编辑距离相似度 ≥ 0.8；
4. 多条匹配时取最近使用的一条，其次取使用频率最高的一条。

历史记录需要同时保存：

- `rawInput`：用户原始输入；
- `selectedQuery`：实际用于搜索的繁体词。

### 4.7 兼容接口 `convertPreferred`

`convertPreferred(input)` 是一个**同步辅助函数**：按 4.4 的排序规则返回第一个候选。

它不是新的用户功能，而是给不需要弹候选框的入口使用：

- AI 语义搜索；
- 无法展示选择框的后台任务；
- 其他需要同步、单一结果的降级场景。

> 卷内搜索、经目/作译者搜索已改为使用与主页相同的候选流程，不再只调用 `convertPreferred`。

示例：

```dart
convertPreferred('干净'); // 词库优先 → '乾淨'
convertPreferred('云何'); // 原字优先 → '云何'
```

这样可以让新旧入口共用同一套候选逻辑，而不必在每个调用点重复写转换规则。后续如果某个入口也接入候选弹层，只需改为使用完整的 `ConversionResult`，`convertPreferred` 仍可作为降级方案。

### 4.8 结果结构

```dart
class ConversionResult {
  final String rawInput;
  final ScriptKind scriptKind;
  final List<String> candidates; // 已按推荐度排序
  final bool requiresChoice;     // candidates.length > 1
  final bool truncated;          // 是否因上限被截断
}
```

同时保留兼容接口：

```dart
String convertPreferred(String input); // 返回第一个候选，供 AI/后台等非交互场景使用
```

## 五、多候选搜索交互

### 5.1 何时显示候选面板

五个搜索入口（首页、全文搜索、卷内搜索、经目查询、作译者查询）都使用**输入框下方的实时候选面板**。

显示规则：

- 输入框获得焦点且内容为空：显示历史记录（不显示标题）；
- 输入框内容非空：不显示完整历史列表，只把高度匹配的历史记录置顶到候选面板；
- 候选面板显示条件：判定为简体或混合输入，且候选数 ≥ 2；
- 输入为繁体、中性、只有单一候选、Goto 表达式或 AI 语义搜索模式时，不显示候选面板；
- 候选生成是同步的字符串处理，不读取本地经文、不计算任何统计数字。

### 5.2 面板内容与排序

面板固定在输入框下方，**不做键盘避让**；高度上限 280，可滚动，**宽度与完整输入框（含图标与按钮区域）一致**。

候选面板使用系统默认的 Material 列表样式，**不显示任何标题或说明文字**。

候选行顺序：

1. **历史高匹配结果**（标「歷史」）；没有历史匹配时使用首选候选；
2. **原始输入**（标「原始輸入」）；
3. 其余转换候选。

去重规则：

- 原始输入与第一行相同时，只保留一行，并合并显示相应标记；
- 历史匹配与原始输入相同时，同样合并标记，不重复占行。

每行只显示候选文字与必要标记，**不显示命中数量、比例或统计状态**。

视觉状态：

- 第一行是默认候选，不加额外高亮；
- 用户点击某一行后，该行短暂显示绿色对勾并立即搜索；
- 不使用金黄色高亮或无限闪烁动画，保持系统默认列表观感；
- 历史标题、原始输入、实际搜寻等提示文字随当前简繁显示模式转换。

### 5.3 不搜索本地经文、不统计数量

候选生成后只等待用户选择（或直接使用首选候选），明确不做以下事情：

- 不读取 `scriptureVolumeStore` 或任何已下载经文；
- 不扫描经文正文，不统计「卷数」「出现次数」「命中位置」；
- 不向 CBETA 服务器请求任何计数；
- 不启动 isolate、后台任务、计时器或进度回调；
- 不根据统计结果重新排列候选。

理由：

- 候选数量有限（每个歧义位置最多 3 个，总计最多 50 个），用户只需要在少量组合中做选择；
- 本地扫描会把简单的搜索变成 CPU 密集任务，带来卡顿、缓存失效、取消与重排等额外复杂度；
- 命中统计只代表本地已下载内容，容易让用户误以为等同于 CBETA 全站结果；
- 不做统计可以让所有入口行为一致、响应即时、实现简单。

各入口的差异只体现在「候选面板是否启用」与「搜索范围」上，与统计无关。

固定优先项（历史匹配、含繁体原文）与基础优先级足以决定候选顺序，见 4.4。

### 5.4 用户选择后

- **点击候选行**：立即用该候选发起搜索，同时把输入框文字替换为该候选；
- **点击历史行**：输入框保留历史原始输入，并立即用历史实际搜索词发起搜索；
- **不选择直接提交**（键盘搜索键或搜索按钮）：使用面板第一行作为实际搜索词，输入框保留用户原始输入；
- 搜索历史保存：
  - `rawInput`（用户输入）；
  - `selectedQuery`（实际搜索词）；
  - 便于下次复现与历史置顶。

### 5.5 焦点与输入法

- 输入框失去焦点、点击面板外部、清空输入时，隐藏面板；
- 面板固定显示在输入框下方，不做键盘遮挡避让；
- 中文输入法组合期间不刷新候选，避免拼音组合阶段候选跳动；
- 候选面板使用 `TapRegion` 与输入框保持焦点关联，点击候选不会先触发失焦。

## 六、繁 → 简显示转换

### 6.1 目标

切换简体显示时：

- 繁体经文不能出现错误简体；
- 罕见的繁体异体字要能正确转回简体；
- 佛学专名不能被拆坏。

### 6.2 算法

1. **词组优先**：对文本做 `phrases_traditional_to_simplified` 最长匹配；
2. 命中词库的片段直接使用推荐简体；
3. 未命中片段逐字查繁→简列表；
4. 单字有多个候选时：
   - 先查保留词库；
   - 没有则取列表第一个；
5. 词库和表都没有的字：保持原字，不猜测。

### 6.3 性能：为什么不能逐位置扫描整个词库

这一段解释的是「整卷经文显示时的转换性能」，与用户输入短查询的场景不同。

**背景**：繁→简转换会应用到整卷经文。一卷可能有 5 万到 15 万字，而词库可能有数万条词组。如果在每一个字符位置都把整个词库尝试匹配一遍，计算量会非常大，导致翻页、滚动、切换简繁时明显卡顿。

**关键观察**：绝大多数繁体字只有一种简体写法，不需要看上下文；真正需要看上下文的只是少数「歧义字」，例如：

- 著 / 着
- 藉 / 借
- 乾 / 干
- 隻 / 只
- 係 / 系
- 臺 / 台
- 週 / 周
- 託 / 托
- 佔 / 占
- 穀 / 谷
- 餘 / 余
- 徵 / 征
- 禦 / 御
- 鬥 / 斗
- 蔔 / 卜
- 鬱 / 郁
- 籲 / 吁
- 紮 / 扎
- 醜 / 丑

**优化策略**：

1. **建立「歧义字集合」**
   只把有两个以上简体候选的繁体字放进去。转换时先判断当前字是否在集合中。
2. **非歧义字直接查单字表**
   一次哈希查找即可完成，O(1)，不需要词库。
3. **只有遇到歧义字时，才在它附近做词组匹配**
   因为词组规则的目的就是解决这些字的上下文问题。例如遇到「著」时，才去看它前面/后面是否组成「著衣」「著名」「顯著」等词。
4. **词库编译成 Trie 或 Aho-Corasick**
   - Trie（前缀树）：匹配时间只与词长有关，与词库总条数无关；
   - Aho-Corasick：一次扫描即可找出所有命中的词组，适合多模式匹配。
5. **整卷结果缓存**
   以 `work:juan:mode:lexiconVersion` 为 key 缓存转换结果；滚动、重绘、再次切换时直接复用，不重复计算。

**直观例子**：

- 十万字经文；
- 假设 2% 的字是歧义字，即约 2000 个位置需要做词组匹配；
- 每个位置只做几次 Trie 跳转；
- 总计算量约几万次，而不是「十万字 × 数万词条」的数十亿次。

这就是「只包含歧义字」「只在歧义字附近匹配词库」「Trie/Aho-Corasick」「整卷缓存」这几条建议的含义。

**与搜索查询的区别**：

- 用户输入的查询通常只有几个到几十个字，可以放心做完整的词库最长匹配；
- 经文显示是长文本，必须做上述优化。

## 七、保留词库的作用与优先级

### 7.1 简 → 繁

作用：

- 让「虽然是简体输入，但在繁体语境中成立」的词保持原样；
- 让歧义词组优先得到正确繁体。

例：

- `云何`、`山谷`、`干戈`、`皇后`、`公里`、`北斗`、`征伐`、`占卜`、`天台宗`、`于闐`、`尸羅`、`咸皆`。

这些词如果没有词库，只靠单字列表会出现：

- 云何 → 雲何
- 皇后 → 皇後
- 干戈 → 幹戈
- 于闐 → 於闐

### 7.2 繁 → 简

作用：

- 保护佛学专名与固定译名；
- 解决「著/着」「藉/借」「乾/干」「隻/只」「係/系」等一对多问题。

例：

- 乾闥婆 → 乾闼婆（而不是干闼婆）
- 著衣 → 着衣（视词库而定）
- 一隻 → 一只
- 關係 → 关系

### 7.3 优先级

1. 人工佛学词库；
2. OpenCC 词组；
3. 单字列表第一个；
4. 原字保留。

## 八、搜索入口的统一策略

| 入口 | 策略 |
|---|---|
| 首页关键字搜索 | 实时候选面板（输入框下方）；不扫描本地经文、不统计数量；先判断 Goto |
| 全文搜索页 | 实时候选面板；不扫描本地经文、不统计数量 |

| 卷内搜索 | 实时候选面板；**不扫描当前卷、不统计**；**不做 Goto 判断** |
| 经目搜索 | 实时候选面板；**只搜元数据，不搜正文**；**不做 Goto 判断** |
| 作译者搜索 | 实时候选面板；**只搜元数据，不搜正文**；**不做 Goto 判断** |
| AI 语义搜索 | 使用原始输入或首选候选，不显示候选面板；不做 Goto 判断 |
| 离线搜索 | 与在线相同，使用完整候选；不统计 |

- 只有首页关键字搜索做 Goto 判断；
- 本地是否已有经文不影响候选弹层与候选排序；
- 候选生成不依赖网络请求，离线时同样可用。

## 九、缓存与失败处理

### 9.1 没有后台任务

- 候选生成是同步的最长匹配与组合，随输入即时完成；
- 不启动 isolate、不读取本地经文、不发送计数请求；
- 因此不需要取消逻辑、分批回传、进度 UI 或重排节流；
- 用户取消弹层、修改输入或离开页面时，只需丢弃本次候选结果。

### 9.2 缓存

- 繁→简显示转换缓存 key：`work:juan:mode:lexiconVersion`；
- 词库（简→繁、繁→简、两个词组表）在启动时加载一次，之后只读；
- 候选结果通常很短，可不缓存；如需缓存，key 至少包含 `rawInput + historicalQuery + lexiconVersion`；
- 词库版本变化时，转换缓存与候选缓存都失效。

### 9.3 失败处理

- 词库加载失败时退回原文搜索，不阻塞用户；
- 候选生成异常时使用原始输入作为唯一候选；
- 不在 UI 线程做重计算；候选生成本身只是短字符串处理。

## 十一、原方案与本方案的差异总结

| 原方案 | 修订后 |
|---|---|
| 按字生成组合 | 可以生成较多组合，但不向服务器发计数请求 |
| 每个组合启动背景线程搜索 | 不启动后台任务；候选同步生成 |
| 扫描本地经文统计卷数/次数 | 不读取、不扫描本地经文，不统计任何数量 |
| 服务端计数、按接口结果排序 | 不统计；按固定优先项 + 候选生成顺序排序 |
| 等待计数完成后再选择 | 候选立即展示，直接可选 |
| 文本编辑下拉框 | 只读下拉/底部弹层 |
| 只判断“全是简体/全是繁体” | 增加混合输入、共用字、中性输入处理 |
| 未定义输入原文优先 | 含至少一个繁体字时，原始输入置顶 |
| 未定义历史优先 | 与历史高度匹配时，历史选择置顶 |
| 繁→简只用单字列表 | 词组优先 + 单字兜底 |
| 未定义离线行为 | 离线同样可生成候选，不做统计 |
| 卷内/经目搜索使用首选转换 | 与主页相同的候选流程 |
| 所有入口都做 Goto 判断 | 仅首页做 Goto 判断 |
| 经目/作译者搜索正文 | 只搜元数据，不搜正文 |

## 十三、结论

方案可行，且比当前实现更准确，但必须按上述修订执行：

- **词库优先、组合可多但不做统计**是可行性的关键：既不请求服务器，也不扫描本地经文；
- **候选立即展示、直接可选**，不需要等待任何计数；
- **候选顺序只由固定优先项与基础优先级决定**，不使用命中数量；
- **候选生成是纯字符串处理**，同步完成，不引入 isolate 或后台任务；
- **Goto 只在首页判断**，卷内/经目/作译者搜索不触发 Goto；
- **经目/作译者搜索只查元数据**，不搜索正文；
- **含繁体字的输入原文优先**，符合用户直觉；
- **历史高度匹配优先**，但必须定义“高度匹配”的阈值；
- **繁→简必须词组化**，否则仍会改坏经文；
- **卷内搜索、经目/作译者搜索**与主页使用同一套候选流程；
- **离线、混合输入、历史记录、其他搜索入口**需要一并设计。

按本方案实施后，可以做到：

- 简体输入不再被错误地强制转换成单一繁体；
- 候选立即可见，用户无需等待统计；
- 不会因为候选统计导致 CBETA 接口压力或本地 UI 卡顿；
- 经文显示不会被简繁转换改坏；
- 原有 Goto、离线阅读、卷内搜索等功能保持可用。

## 十五、卸载后的数据保留

Android 端启用系统自动备份与卸载保留提示：

- `android:allowBackup="true"`；
- `backup_rules.xml` 与 `data_extraction_rules.xml` 包含 `sharedpref`、`file`、`database`、`external` 域，覆盖搜索记录、设置与离线经文；
- `android:hasFragileUserData="true"`：卸载时系统会询问是否保留应用数据。

注意：自动备份依赖设备的备份开关与云端配额，不能保证在所有设备上跨卸载恢复；卸载对话框中是否勾选保留数据也由用户决定。
